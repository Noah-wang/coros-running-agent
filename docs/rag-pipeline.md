# RAG 全流程：成熟方案的组成，与本项目的对照

这份文档把一套生产级 RAG 拆成 20 个环节，逐个说明「这一层要解决什么」，
然后对照本项目的实现，标出做对的地方、真实缺陷和要不要补。

评级含义：

```text
✅ 达标    和成熟方案做的事情一致，或规模上不需要更多
⚠️ 部分    有雏形但缺关键能力
🔴 缺口    没有，且构成真实短板
—  不适用  单人单机场景不需要
```

## 1. 数据接入（Ingestion / Connectors）

把散落各处的原始文档弄进流水线，并持续保持同步。

成熟方案要解决：

```text
连接器        本地盘 / S3 / Google Drive / Notion / Confluence / Slack / 数据库 / 爬虫
增量同步      只处理变化的文档，靠 mtime、etag、内容哈希、webhook、数据库 CDC 检测
删除传播      源文档删了，索引里对应的块必须跟着删，否则会检索出已删除内容
权限元数据    ACL 随文档一路带到检索层做过滤，否则跨权限泄露
调度          定时轮询 vs webhook 推送
幂等          失败了可以直接重跑，不会产生重复数据或叠加副作用
原子性        中途失败不能留下半个索引
原始副本      保留原文件，换解析器重跑时不用重新下载
文档级元数据  标题、作者、时间、版本、来源 URL
```

本项目有两条接入路径：PDF 手动放进 `books/`；B站字幕通过 `!running-video BV号`
抓取后写入 `videos/{时间戳}-{BV}.md`，再触发索引重建。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 连接器 | 2 个，命令触发 | ✅ 单人够用 |
| 增量同步 | 按内容哈希复用向量，只嵌入变化的子块 | ✅ |
| 删除传播 | 切块全量重来，源文件消失则块自然消失 | ✅ |
| 权限元数据 | 频道级隔离，非文档级 | — |
| 调度 | 手动命令 | ✅ |
| 幂等 | 重跑产出完全一致，还能从撕裂状态自愈 | ✅ |
| 原子性 | 四个文件先写 .tmp，最后一起 rename 就位 | ✅ |
| 持久性 | 没有 fsync，整机断电理论上仍可能丢 | ⚠️ |
| 原始副本 | PDF 和字幕 md 都保留 | ✅ |
| 文档级元数据 | 视频有头部，PDF 完全没有 | ⚠️ |

**做对的地方。** 切块全量重建、只对嵌入做增量，这个组合同时拿到了两个好处：
嵌入省 97% 的 API 调用，而删除传播不用写任何额外逻辑。如果连切块也做增量，
就必须显式维护「源文件 → 块 ID」的反查并处理删除，那是常见的漏洞来源。

**幂等和原子性是两件事。** 这两个概念很容易混为一谈，本项目一开始只有前者，
后来把后者也补上了：

```text
幂等    同一个操作做一次和做多次结果一样，失败了可以放心重跑
原子    要么全部完成要么完全没发生，不存在中间态
```

实测幂等成立：连跑两次，`chunks.json` 和 `index.json` 的 sha256 完全相同，
向量零重算，唯一变化的是 `build_info.json` 里的时间戳——那是「这次运行」的元信息，
不是内容。

**而且它能自愈。** 手动删掉 5 条向量制造撕裂状态后重跑，只补算了那 5 条，索引恢复正常。
这正是幂等的价值：失败了不用想怎么修，重跑一遍就行。

**当时的真实缺陷是原子性。** `main()` 的顺序是 chunks.json → index.json →
build_info.json → embeddings.json，最后一步最慢也最容易失败。开发期间真的崩过两次
（键名写错、`datetime` 没导入），两次都留下「新块 + 旧向量」的中间态。

运行时有一层护栏兜住了：`search_knowledge` 检查向量覆盖的父块数是否等于块数，
对不上就降级到关键词检索。所以中间态不会产生错误结果，只会**静默降级**——
回答质量变差但没有任何报错。

**这一点已经修掉了。** 四个文件先全部写成 `.tmp`，最后一起 `rename` 就位。
同一文件系统内的 rename 只是改一条目录项，是原子的：读的人要么看到完整的旧文件，
要么看到完整的新文件。

危险窗口从「写 embeddings 要等的几十秒 API 时间」缩到了「四次 rename 的几微秒」。
理论上四次 rename 之间仍有残余窗口，真正的跨文件原子性要靠整个目录替换，
但对单机单人场景是过度设计。

实测：在嵌入阶段人为抛出 `KeyboardInterrupt`，四个索引文件的 sha256
一个字节都没变，临时文件也清理干净了。这里捕获的是 `BaseException` 而不是
`Exception`——Ctrl+C 抛的 `KeyboardInterrupt` 不属于 `Exception`，
而它恰恰是最现实的中断方式。

**为什么 rename 能原子而写文件不能。** 目录本质上是一张「名字 → 内容块」的对照表：

```text
write_text   改的是「内容」：清空原内容块，再一点点写进去
             名字始终指着同一块内容，整个过程都是中间态

rename       改的是「指针」：目录表里那一行从旧内容块改指向新内容块
             改一个指针可以是不可分割的，改几 MB 内容不可能
```

所以这个技巧的本质不是「写得更快」，而是**把慢的部分挪到一个没人在看的名字上，
只留一次指针切换暴露给读者**。

**旧内容什么时候消失。** 靠引用计数：目录里的名字和进程打开的句柄都算引用。
rename 之后旧内容失去名字，但如果还有进程开着它，内容会一直存在到那个进程关闭。

这带来一个有用的推论：**在 rename 之前就打开文件的读者，会完整读完旧版本，
不会读到一半被换掉。** 所以 ingest 替换索引时，正在检索的 bot 或 web 进程
拿到的始终是一个一致的快照。

**边界：原子 ≠ 持久。** 这两个概念相邻但不同：

```text
atomicity    要么全成要么全不成，不存在中间态        ✅ rename 保证
durability   一旦说成功了，断电也不会丢              ❌ 需要 fsync
```

`write_text` 之后数据可能还在操作系统的页缓存里没落盘，rename 也只是改目录项。
完整的持久化要 `fsync(tmp)` → `rename` → `fsync(目录)` 三步。

本项目没做 fsync，所以准确说法是 **atomic but not durable**：
进程崩溃、Ctrl+C、报错都能防住（这是实际会遇到的），整机断电理论上仍可能丢。
数据库会做完整 fsync，代价是每次写盘慢一个数量级；对「手动跑 ingest、
崩了重跑一次就自愈」的场景不值得，但知道这条边界在哪比假装它不存在好。

英文里这套做法叫 **atomic write** / **atomic file replacement**，
实现手段叫 **write-rename pattern**，底层是 POSIX 的 `rename(2)`。
Python 用 `os.replace()` 而不是 `os.rename()`，因为后者在 Windows 上目标存在会报错。
描述这类保证的术语是 **crash consistency**（崩溃一致性）。

## 2. 解析（Parsing / Extraction）

把二进制文件变成带结构的文本。这是全流程里最容易被低估的一层。

成熟方案要解决：

```text
版面感知      多栏、页眉页脚、脚注、图注的正确阅读顺序
表格提取      表格要变成结构化数据，而不是拍平成一串数字
标题层级      章节结构要保留，供分块和元数据使用
图片 OCR      扫描件、图中文字
公式          LaTeX / MathML
多模态        图表本身作为检索单元
```

本项目用 `pypdf.extract_text()` 逐页取文本流，视频侧直接拿字幕文本。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 版面感知 | 无，纯文本流 | 🔴 |
| 表格提取 | 无 | 🔴 |
| 标题层级 | 无 | ⚠️ |
| OCR | 不需要（PDF 有文本层） | — |
| 公式 | 不需要 | — |

**这是本项目最大的短板。** 丹尼尔斯这本书的核心价值之一是 VDOT 配速对照表，
而索引里能找到的只有孤零零的表格标题：

```text
相同配速、不同距离下消耗的时间
时间和配速的转换
```

表名还在，表格内容没了。后面所有环节做得再好，也捞不出一个解析阶段没提取出来的表格。

**为什么检索指标没暴露这个问题。** 评测集里的定点题问的是「周跑量的10%」
「90~120秒」这类散文中的数字，恰好避开了表格。指标漂亮，但测的是残缺语料。

**意外的补救。** `training_paces` 工具用 Daniels/Gilbert 公式直接算配速，
实测与书中表格误差 1~2 秒。所以最需要查表的场景反而不依赖表格了——
这是个碰巧正确的选择，不是设计出来的。

要补的话，先往评测集加「表格类问题」，否则换了解析器也不知道好没好。

## 3. 清洗与去噪（Cleaning）

去掉不承载信息、但会污染检索的内容。

成熟方案要解决：

```text
页眉页脚      每页重复的水印、书名、页码
模板文本      版权声明、免责声明、导航菜单
重复段落      同一内容在多处出现
空块过短块    没有信息量却占据向量和 top-k 名额
编码问题      乱码、控制字符、全半角
```

本项目实现在 `find_boilerplate_lines` / `strip_boilerplate` / `filter_chunks`。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 页眉页脚 | 按行统计，铺满 5% 以上页面的短行删除 | ✅ |
| 空块过短块 | 空块和 40 字符以下丢弃 | ✅ |
| 重复段落 | 靠页眉页脚规则顺带解决 | ✅ |
| 编码 | `normalize_text` 去空字符、压空白 | ✅ |

体检发现的问题和修复效果：

```text
修复前  304 块中 72 块是空的（24%），每块还白算一条向量
        水印重复 286 次，表注重复 35 次，内容和向量完全相同
        p25 长度只有 30 字符
修复后  145 块，0 空块，0 过短块，0 重复
        删除 321 行页眉页脚
```

**关键设计：必须在跨页合并之前按行处理。** 合并成整篇之后，水印会混进正常块的
正文里，那时再按块去重就晚了。

**踩过的坑：阈值不能用绝对次数。** 第一版用「重复 5 次以上」，把正文里的
「热身，然后进行下列训练：」也删了——这句话在训练章节本来就会反复出现。
改成按页数取相对阈值（铺满 5% 以上页面）之后只删水印和表注。

## 4. 分块（Chunking）

把长文档切成检索单元。

成熟方案要解决：

```text
结构优先      有天然结构就按结构切：JSON 按记录、代码按函数、FAQ 按条目
语义边界      没有结构才按长度，且不能在句子中间下刀
物理边界      页、屏、段这些排版单位不是语义单位，不能直接当边界
重叠          相邻块共享一段文字，保住卡在边界上的内容
层级          父子块 / 多粒度索引
块大小        要实测，不是抄一个默认值
```

本项目实现：`build_document`（跨页合并）→ `find_break`（句末标点，退而求其次找
逗号顿号，都没有才硬切）→ `chunk_document`（重叠起点也对齐边界）→
`split_children`（父块 1200、子块 700）。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 结构优先 | 书和字幕都是自由文本，无结构可用 | — |
| 语义边界 | 两级断点，句中开头的块降到 0.7% | ✅ |
| 物理边界 | 跨页合并，138/145 块横跨页边界 | ✅ |
| 重叠 | 重叠起点也对齐句子边界 | ✅ |
| 层级 | 父子块，子块匹配、父块投喂 | ✅ |
| 块大小 | 三组配置实测比较 | ✅ |

**旧实现的真相：真实策略是「一页一块」。** 按页调用切块函数，而书的中位页长
只有 369 字符，远小于 `CHUNK_SIZE=1200`——286 页产出 295 块，其中 277 页恰好 1 块。
那个参数对 97% 的页面从未生效，块大小实际由 PDF 排版决定。

**overlap 也几乎从未触发。** 重叠只发生在同一次切分循环的相邻块之间，
而「下一页」是另一次函数调用。287 页里只有 10 页产生了多于 1 块，
也就是 `CHUNK_OVERLAP=180` 一共只在这 10 页内部起过作用，286 个页边界全是硬切。

**重叠起点必须也对齐边界。** 直接用 `end - CHUNK_OVERLAP` 会退回到上一块的
句子中间，导致几乎每块都从半句话开始。修复后视频第 2 块从 `'的安排自己的训练'`
变成了 `'然后再去灵活的安排自己的训练'`。

## 5. 上下文增强（Contextual Enrichment）

块被切出来之后会丢失它在原文里的位置感，这一层把上下文补回去。

成熟方案要解决：

```text
指代消解      块里的「他」「它」「这本书」失去先行词
文档级身份    这块属于哪份文档、哪一章
情境说明      用 LLM 为每块生成一两句「这块在讲什么」，拼在前面再嵌入
派生内容      为每块生成假设问题、摘要，一并索引
元数据注入    时间、作者、类型进入可过滤字段
```

本项目为每块拼一个静态前缀：书是 `《书名》 第N页`，视频是 `B站跑步视频字幕 BV号`。
嵌入用「前缀 + 原文」，展示只用原文。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 文档级身份 | 静态前缀，零成本 | ✅ |
| 指代消解 | 未做 | ⚠️ |
| LLM 情境说明 | 未做 | ⚠️ |
| 派生内容 | 未做 | — |
| 元数据注入 | `kind` / `page` / `page_end` 存了但检索不用 | ⚠️ |

**修复的具体问题：视频 md 的头部原来只落在第 1 块里**，第 2 到第 9 块完全不知道
自己是视频、是哪个视频。现在每块嵌入时都带上来源身份。

**关键原则：加前缀，不改正文。** 因为引用展示的是 `chunk["text"]` 并挂着页码，
一旦用 LLM 把块里的「它」改写成具体名词，这段就不再是页面上真实存在的文字，
但页码还在——等于伪造出处。

**有一类指代无解。** 字幕里的「上一期我们讲了有氧耐力」，那期视频根本不在知识库里。
传全文没用，改写还会编一个出来。能做的只有识别出来并标为已知限制。

## 6. 嵌入（Embedding）

把文本变成向量。

成熟方案要解决：

```text
模型选择      维度、语种、领域适配、成本
批量          控制单次请求的条数和 token 上限
增量          内容没变就不重算
版本管理      换模型意味着整个索引作废，要能检测和迁移
异步与重试    限流、超时、部分失败
```

本项目用 `embed_texts` 批量 20 条，按内容哈希增量复用。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 模型选择 | qwen3.7-text-embedding，1024 维 | ✅ |
| 批量 | 20 条一批，可配 | ✅ |
| 增量 | 按内容 sha256 复用 | ✅ |
| 版本管理 | 索引记录模型名，不一致时整份缓存作废并降级检索 | ✅ |
| 重试 | 无 | ⚠️ |

**增量的实测效果：**

```text
首次迁移      复用 0/290，全量重算
内容未变      复用 290/290，零 API 调用
新增一份视频  复用 290/291，只调 1 次（原来 15 次）
删除该视频    块和向量全部清除，无残留
```

**用内容哈希而不是块 ID 作缓存键。** 块 ID 里带页码，页码会随分块策略变化；
而内容没变就没必要重算。同时哈希覆盖了「前缀 + 正文」，所以页码变了会正确地触发重算。

## 7. 索引（Indexing）

把向量和文本组织成可检索的结构。

成熟方案要解决：

```text
向量索引      HNSW / IVF 等近似最近邻，把 O(N) 降到近似 O(log N)
倒排索引      BM25 关键词检索
元数据索引    支持 where 条件过滤
混合存储      向量、原文、元数据在一起，避免二次查询
分片与副本    规模和可用性
```

本项目把索引存成四个 JSON 文件：`chunks.json`（父块原文与元数据）、
`embeddings.json`（子块向量）、`index.json`（BM25 用的分词表）、
`build_info.json`（构建配置指纹）。检索是 NumPy 暴力矩阵乘法。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 向量索引 | 暴力全量比对 | ✅ 规模不需要 ANN |
| 倒排索引 | BM25 + 分词表 | ✅ |
| 元数据索引 | 字段存了但检索时不过滤 | ⚠️ |
| 混合存储 | 全在本地 JSON | ✅ |
| 分片副本 | 无 | — |

**为什么不需要向量库。** 业界共识是 10 万条向量以下 NumPy 暴力搜索就够，
本项目只有 290 条，差三个数量级。而且暴力搜索在这个规模下不只是够用，是更好：

```text
召回率 100%   ANN 索引是近似的，会静默漏掉相关内容，
              而这种漏检发生在模型看到之前，根本察觉不到
零运维        「数据库」就是一个文件，没有端口、容器和额外进程
```

还有一条反直觉的：如果向量频繁变动，建 ANN 索引的开销可能超过搜索省下的时间。

**真正该优化的不是存储，是别用 Python 循环做数值计算：**

```text
纯 Python 逐条算余弦    38.37 ms
NumPy 归一化矩阵乘法     0.19 ms      快约 200 倍
```

## 8. 索引运维（Index Operations）

索引不是建完就完事，它要跟着语料和代码一起演进。

成熟方案要解决：

```text
增量更新      只重建变化的部分
原子切换      新索引就绪前，旧索引继续服务
版本回滚      新索引效果变差能退回去
配置追溯      能知道这份索引是用什么参数建的
一致性校验    向量数、块数、模型名要对得上
```

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 增量更新 | 嵌入按哈希增量，切块全量（本地计算，免费） | ✅ |
| 原子切换 | .tmp + rename | ✅ |
| 版本回滚 | 无（部署前手动 tar 备份） | ⚠️ |
| 配置追溯 | `build_info.json` 记录构建配置 | ✅ |
| 一致性校验 | 检索时校验覆盖数和模型名，不一致则降级 | ✅ |

**配置漂移是这一层最隐蔽的问题。** 做父子块实验时用命令行环境变量
`CHILD_CHUNK_SIZE=700` 建了索引，但代码默认值还是 400。服务器的索引和产生它的
代码从那一刻起就对不上了，而且完全没有症状——索引本身好好的，检索正常，评测全绿。
直到有人重跑一次 ingest（导入新视频会自动触发），索引就会被悄悄换成劣化配置。

**评测抓不到这一类问题**，因为评测量的是索引的检索效果，不是「产生索引的配置
和当前代码一不一致」。

现在的做法是：分块配置收进 `src/runtime/chunking.py` 单一来源，建索引时把配置
写进 `build_info.json`，体检时逐项比对：

```text
{ "child_chunk_size": "索引=700 当前代码=400" }
```

## 9. 查询理解（Query Understanding）

用户问的话不一定适合直接拿去检索。

成熟方案要解决：

```text
查询改写      口语化、有指代、有错别字的问题改写成检索友好的形式
查询扩展      同义词、上位词、领域术语
HyDE          先让模型编一个假想答案，用答案去检索
多查询        把一个复杂问题拆成几个子查询分别检索
意图识别      是事实查询还是开放讨论，决定检索策略
```

本项目做了两件事：多轮对话时把上一轮用户消息拼进检索 query；`_tokenize` 里有一张
手写同义词表（阈值 → threshold / tempo / lactate / 乳酸 / 门槛）。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 查询改写 | 未做 | ⚠️ |
| 查询扩展 | 手写同义词表 | ⚠️ |
| HyDE | 未做 | — |
| 多查询 | 未做 | — |
| 上下文补全 | 多轮时拼上一轮消息 | ✅ |

**多轮拼接解决的是真实问题。** 追问之后用户往往只回一句「1 每周40公里 2 主要是间歇」，
单独拿它去检索会完全跑偏。拼上上一轮的问题就能保住话题：

```text
'半马1:40全马4:30怎么练\n1 每周40公里 2 主要是间歇'
```

**同义词表是典型的启发式**：便宜、不保证对、表外的词一个都不认。它能工作是因为
领域窄、术语固定。语料一旦扩展到其他运动就得重写。

## 10. 路由（Routing）

决定这个问题该交给谁、查哪个索引、用哪个工具。

成熟方案要解决：

```text
数据源选择    多个知识库时选哪个
工具选择      查知识库、查数据库、调 API、还是直接回答
权限过滤      当前用户能看哪些源
拒识          不该回答的问题要能拒绝
置信度        判断不确定时要能兜底
```

本项目在 `MainAgentOrchestrator` 做自然语言路由，输出结构化 intent，
配白名单校验、置信度阈值和参数合法性检查。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 能力选择 | LLM 输出 JSON intent | ✅ |
| 权限过滤 | Discord 频道白名单，公开 Web 入口只读 | ✅ |
| 拒识 | 闲聊和意图不明返回 none | ✅ |
| 置信度 | 低于阈值拒绝 | ✅ |
| 参数校验 | 非法参数拒绝 | ✅ |
| 检查 | 建议用你自己的 golden set 覆盖以上全部 | ✅ |

**这一层是本项目做得最完整的部分之一**：路由先输出结构化 intent，
再经过命令白名单、置信度阈值和参数合法性检查。

**还有一条捷径。** 教练追问之后会把问题存成 pending，下一条消息进来时直接投给
`running`，跳过自然语言路由。因为裸答案（「1 每周40公里」）交给路由器很容易被判成
`none` 或置信度不足，用户会觉得 Agent 突然不理人了。这条捷径不绕过频道白名单。

## 11. 检索（Retrieval）

拿查询去索引里捞候选。

成熟方案要解决：

```text
向量检索      语义相似
关键词检索    BM25，对罕见词、型号、错误码更准
元数据过滤    where 条件先筛掉不相关的
多路召回      不同策略各出一份候选
候选数量      召回阶段要比最终 top-k 多，给融合和重排留材料
```

本项目 `search_knowledge` 走父子块向量检索：子块算相似度，按父块取最高分归并。
`search_knowledge_keyword` 是 BM25 兜底。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 向量检索 | 父子块 + NumPy 矩阵运算 | ✅ |
| 关键词检索 | BM25（词频饱和 + 长度归一化），仅作兜底 | ✅ |
| 元数据过滤 | 未做 | ⚠️ |
| 多路召回 | 实现了，实测更差已关闭 | ✅ 有结论 |
| 降级 | 向量不可用时自动退关键词 | ✅ |

**父子块归并的细节：多个子块可能命中同一个父块，按最高分归并**，
避免一个父块占掉多个 top-k 名额。

**关键词检索原来单次要 207 毫秒**，因为每次都遍历 32 万个 token 重建词频和
文档频率表。这两张表完全由索引文件决定，加 mtime 缓存后降到 23 毫秒。

## 12. 融合（Fusion）

把多路召回的结果合成一份排序。

成熟方案要解决：

```text
分数归一化    余弦相似度和 BM25 分数量纲完全不同，不能直接相加
排名融合      RRF 只看名次不看分数，天然免疫量纲问题
权重          不同召回器可信度不同
去重          同一文档被多路召回时只留一份
```

本项目实现了加权 RRF：`score = Σ 权重 / (60 + 名次)`。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| RRF | 实现了 | ✅ |
| 权重 | 可配 `RAG_VECTOR_WEIGHT` | ✅ |
| 默认开启 | **否，实测更差** | ✅ 有依据 |

**实测数据推翻了「混合检索一定更好」这条主流建议：**

```text
                 纯向量    等权融合   向量权重3   向量权重8
hit@k             0.97      0.93       0.93       1.00
hit@1             0.87      0.83       0.80       0.80
mrr@k             0.91      0.88       0.86       0.87
book_hit          1.00      0.91       0.91       1.00
```

更说明问题的是权重曲线：向量权重从 1 加到 8（此时关键词几乎不起作用）指标才
逐步回到纯向量水平——**关键词的每一分贡献都是负的，不是权重没调好**。

后来把关键词那一路从 TF-IDF 换成 BM25 又重测了一次，融合的总体判决没有改变，
但暴露出一个之前被掩盖的细节：

```text
              纯向量    混合 + BM25
book_hit       1.00       0.91      ← 书上丢了
video_hit      0.86       1.00      ← 视频全中
```

**混合不是全面变差，是在视频上赢、在书上输，而书占语料 94%，所以总账是亏的。**
赢的那一项正是资料预言的场景：`video_blood_volume` 这类查询里的「总血量」是罕见词，
BM25 能精确命中，纯向量下它排第 4、top-3 拿不到。

之前用 TF-IDF 时这个 trade-off 看不出来，因为写死的 +100 短语加权让关键词排序
退化成了规则匹配。换成 BM25 之后分数分布正常，才看清赢在哪、输在哪。

代码和 `RAG_HYBRID_ENABLED` 开关保留。如果语料结构变化（视频占比上升，
或者开始大量出现型号、数值类查询），这个结论可能翻转，而现在有一个
不被畸变污染的关键词检索可以用来重测。

## 13. 重排（Reranking）

用更贵但更准的模型对候选重新排序。

成熟方案要解决：

```text
交叉编码      query 和候选一起进模型，比双塔向量准得多
候选规模      通常先粗召回 100~150 条，再重排取前几条
延迟与成本    每次查询都要跑，是在线成本
```

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 重排 | 未做 | ⚠️ |

**不做是有依据的。** 重排解决的是「候选里有正确答案但排序不对」，
而本项目唯一的失败用例 `video_blood_volume` 是命中块排第 4、top-3 根本拿不到——
**那是召回问题不是排序问题**，重排帮不上。

hit@1 已经 0.87，剩下的空间也不大。等召回率先出现明显缺口再考虑。

## 14. 上下文组装（Context Assembly）

把检索结果拼成送进模型的那段文字。

成熟方案要解决：

```text
top-k 选择    条数越多越不容易漏，但塞进 prompt 的无关内容也越多
去重          内容重叠的块只留一份
压缩          用小模型把长块压成要点
排序          相关度最高的放在开头或结尾，避开 lost-in-the-middle
token 预算    和对话历史、系统提示、工具定义共同分配
```

本项目 top-k = 3，父子块按最高分归并算一种去重。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| top-k | 3，由评测数据选定 | ✅ |
| 去重 | 父块归并 | ✅ |
| 压缩 | 未做 | — |
| 排序 | 按相关度降序 | ✅ |
| 预算 | 未显式管理 | ⚠️ |

**从 5 降到 3 是评测驱动的决定：** 30 个用例的命中块全部落在前 3 名，
hit@3 与 hit@5 相同，第 4、5 名从未被用到却要占掉约 40% 的检索上下文——
而且这段上下文在工具调用循环的每一轮都会重发。

```text
top-5   平均 6134 字符
top-3   平均 3684 字符    省 40%，命中率零损失
```

**一个必须守住的纪律：评测用的 k 必须和生产一致。** 曾经 judge 写死 5 而生产是 3，
`video_hit_rate` 一直虚报 1.00，真实值是 0.86。现在两边都从
`src.runtime.rag.DEFAULT_TOP_K` 读同一个常量。

## 15. 生成（Generation）

把问题、上下文和历史交给模型产出回答。

成熟方案要解决：

```text
提示词结构    问题、检索内容、历史、记忆各自的位置和标注
引用归因      回答里的论断能追溯到具体来源
拒答          证据不足时要说不知道，而不是编
长度与风格    和问题复杂度匹配
工具调用      需要精确计算或实时数据时调工具而不是猜
```

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 提示词结构 | 问题 / 摘要 / 待回答问题 / 长期记忆 / 检索片段分块注入 | ✅ |
| 引用归因 | 一行来源，展示原文不改写 | ✅ |
| 拒答 | 明确要求证据不足时说明 | ✅ |
| 长度风格 | 对话为默认，结构化为例外 | ✅ |
| 工具调用 | 配速换算、日期、写档案、知识库体检四个工具 | ✅ |

**引用展示的取舍。** 原来每条回答后面跟三段各 220 字的原文摘录，整块 841 字符，
而对话式回答本身只有一两百字——引用比答案长四到八倍。改成一行紧凑来源后降到 69 字符，
溯源信息保留但不喧宾夺主。保留 `RAG_CITATION_STYLE` 三档可切回完整引用。

**模板绑架回答是另一个坑。** 问答和运动报告原本用着结构几乎相同的四段模板，
而且报告侧的质量审查器硬性校验「必须包含问题重述、当前判断、数据依据、下一步、边界」——
模型就算想好好说话也会被打回重写。现在审查器只查内容和安全，明确允许三五句话讲完。

```text
安全过滤      医疗、法律、金融等高风险领域的边界

```

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 质量审查 | 运动报告有 critic 节点，问答侧没有 | ⚠️ |
| 安全边界 | 提示词层面禁止医疗诊断和成绩承诺 | ✅ |
| 引用校验 | 未做 | ⚠️ |
| 格式校验 | 路由的 JSON 有白名单和参数校验 | ✅ |

运动报告走 LangGraph，生成后经 `critic_review` 审查，不合格则 `revise_report` 修订。

## 17. 评测（Evaluation）

没有这一层，前面所有环节的调整都是拍脑袋。

成熟方案要解决：

```text
检索指标      hit@k、recall@k、MRR、nDCG
生成指标      忠实度、相关性、有没有幻觉
golden set    固化的问答对，覆盖典型和边界场景
回归防护      阈值设在基线略下方，改动变差要能拦住
在线指标      用户点踩、追问率、会话长度
```

开源版不附带个人数据集。建议你用自己的资料建立 golden set，
至少覆盖自然语言路由和 RAG 检索两类问题。

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 检索指标 | hit@k、hit@1、MRR、分来源、分题型 共 7 项 | ✅ |
| golden set | 30 个用例，含 8 道定点事实题 | ✅ |
| 回归防护 | 阈值设在基线略下方 | ✅ |
| 实验记录 | spec 里存了四组配置的完整对比 | ✅ |
| 生成指标 | 未做 | ⚠️ |
| 在线指标 | 未做 | ⚠️ |

**几个刻意的设计决定：**

```text
判据用关键词而不是页码   页码随分块漂移，而分块正是这套评测要衡量的东西
报告实际检索模式         检索会静默降级到关键词，不报告的话指标好看但没测到向量链路
视频单独出指标           视频只占索引 6%，用视频独有术语出题防止它被淹没
定点题单独出指标         它们对块粒度最敏感
索引缺失时跳过而非失败   本地没索引也能跑其他 suite
```

**这一层是本项目相对成熟方案最不落后的部分**，甚至超出不少真实生产系统——
大量线上 RAG 没有 golden set，全靠人肉体感判断好坏。

成熟方案要解决：

```text
链路追踪      一次问答里检索了什么、召回哪些块、模型调了几次
用户反馈      点赞点踩、复制、追问，回流成评测数据

```

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 结构化日志 | 路由决策、工具调用、pending 命中都有日志 | ✅ |
| 链路追踪 | 无聚合，只能翻 journalctl | ⚠️ |
| 用户反馈 | 无 | ⚠️ |

```text
orchestrator natural_language_route_raw ... confidence: 0.95
running tool_call round=0 name=save_running_profile arguments={...}
```

## 19. 权限与多租户（Access Control）

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 文档级 ACL | 无 | — |
| 租户隔离 | 无 | — |
| 频道隔离 | 能力绑定频道，非指定频道不可用 | ✅ |
| 会话隔离 | Discord 按频道、Web 按浏览器 session | ✅ |
| 公开入口只读 | Web 入口三层拦截写操作 | ✅ |

单人单机场景不需要文档级权限。但公开的 Web 入口暴露出另一类问题：
**不是「谁能看哪份文档」，而是「公开入口和私人数据之间缺一道边界」。**

个人训练档案是通过 `format_memory_for_prompt` **无条件注入 prompt** 的，
不经过检索。这意味着再完善的检索过滤也拦不住它——数据压根不走检索那条路。
这是两条不同的泄露路径：

```text
检索层泄露    向量空间里没有权限这个维度，语义相近就会被捞出来
              修法是前置过滤，让不该看的块不参与相似度计算
Prompt 层泄露 数据无条件进上下文，用户甚至不用问相关问题
              修法只有一个：不该给的根本不放进去
```

第二条比第一条更根本，因为它是无条件的；第一条依赖「用户身份被正确传递到检索层」，
链路长、容易漏。

按需求保留了个人档案的**只读**暴露，但用三层拦住了所有写操作：

```text
命令白名单    WEB_COMMANDS 去掉 feel 和 running-video 这类纯写命令
工具集裁剪    Web 入口构建的工具注册表不含 save_running_profile
```

第三层最关键：前两层拦的是命令，而 `save_running_profile` 是模型在 `running`
对话**内部**自主调用的，命令白名单管不到它。写污染比读泄露更麻烦——
陌生人往长期记忆里塞的内容，之后会被当成用户说过的事实用于生成训练建议，
而用户不会察觉。

## 20. 缓存（Caching）

| 子问题 | 本项目 | 评级 |
|---|---|---|
| 索引缓存 | 按文件 mtime 缓存，重建自动失效 | ✅ |
| 关键词表缓存 | 词频和文档频率预计算 | ✅ |
| 向量矩阵缓存 | 归一化矩阵只算一次 | ✅ |
| embedding 缓存 | 按内容哈希复用 | ✅ |
| 查询缓存 | 无 | — |

优化前后：

```text
每次查询重解析 3.2MB embeddings.json    137 ms
加 mtime 缓存                            0.05 ms
关键词检索重建 32 万 token 的统计表      207 ms
加缓存                                    23 ms
纯 Python 逐条算余弦                     38.37 ms
NumPy 矩阵乘法                            0.19 ms
```

用 mtime 当缓存键，重建索引后自动失效，不需要手动清理，也不怕 web 和 bot
两个进程各自持有旧数据。

## 总结：本项目在这条流水线上的位置

**中段扎实。** 清洗、分块、路由、生成、评测、缓存这几层达到或接近成熟方案水准，
其中评测体系和配置漂移检测甚至超出多数真实生产系统。

**头部有真实缺口。** 解析层用纯文本流提取，全书的配速表全部丢失。
这是唯一一个「后面做得再好也补不回来」的环节。

**尾部缺的是优化层。** 重排、查询改写、生成侧审查缺失，但这些都是锦上添花，
而且有数据表明其中一部分（重排、混合检索）对当前规模没有收益。

**三个被实测否掉的主流建议：** 向量库（规模差三个数量级）、
混合检索融合（纯向量已饱和，融合只会挤出正确结果）、
重排（失败用例是召回问题不是排序问题）。能说出「这条不适用于我」而不是照抄，
靠的正是第 17 层。

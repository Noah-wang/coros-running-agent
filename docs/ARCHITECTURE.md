# 架构与设计取舍

README 讲了系统长什么样。这份文档讲**为什么长成这样**，
以及每个决定是被什么具体的失败推着做出来的。

---

## 1. 主 Agent：从分类器到循环

### 原来的样子

```
用户消息 → 模型分类 → 选一个命令 → 执行 → 输出
```

模型只做一件事：把一句话映射成一个命令名。命令执行完就结束。

### 它是怎么坏的

问「我一共跑过几场比赛」，分类器选了「列出运动记录」，
于是倒出 20 条 Indoor Run 的流水。

问题不在于分类器选错了——在它能看到的信息里，那个选择并不离谱。
问题在于**它只有一次机会，而且这次机会在看到任何数据之前**。
一个人类助理会先去看一眼比赛记录，发现不对，再换个地方查。分类器做不到。

### 现在的样子

```python
while round < MAX_ROUNDS:
    response = await model(prompt, history, tools=registry.schemas())
    if not response.tool_calls:
        return response.content
    for call in response.tool_calls:
        result = await registry.execute(call)
        history.append(result)
```

模型拿到工具表，调一个，看结果，再决定下一步。**决定发生在看到数据之后。**

### 保留了什么

`!coros-pb` 这类显式命令仍然走快速通道，绕过循环直接执行。
用户打命令就是要确定的输出，让模型再想一遍只会增加延迟和不确定性。

旧的分类器留在 `MAIN_AGENT_LOOP_ENABLED` 开关后面。
循环模式延迟和成本都更高，**万一线上表现不好要能一键切回去**。

## 2. 幻觉：一个结构问题，不是提示词问题

### 现象

第三轮对话，模型说「你的秦皇岛半马成绩是 1:41:05」。
没有这场比赛，也没有这个成绩。

它是从**对话历史**里推出来的：前两轮提到过半马，提到过某个成绩，
模型把它们拼成了一个看起来合理的事实。

### 提示词修不好

加了「不要编造」「只说工具返回里有的」——第一轮第二轮都对，第三轮又犯。
**因为历史里的数字长得和工具返回的数字一模一样。**
模型没有办法区分「这是我上一轮说的」和「这是数据源给的」。

### 结构修法

```python
run_tool_loop(..., force_first_tool=True)
```

`tool_choice="required"`：第一轮**必须**调工具，不允许直接开口说话。
配一个逃生口 `no_lookup_needed`，让「今天天气不错」这种真的不需要查的问题
有地方去。

现在「不查就答」在结构上不可能，而不是被提示词劝阻。

### 副作用

DeepSeek 在 `tool_choice="required"` 下**不输出 `content`**，
于是 ReAct 的 Thought 消失了——前端本来靠它显示「正在做什么」。

解决办法是把理由挪进工具参数：

```python
def schema(self):
    params["why"] = {"type": "string", "description": "为什么要调这个工具"}
    required.append("why")   # 必填
```

模型必须在调用工具时说明理由，理由变成了结构化字段而不是自由文本。
`ToolRegistry.execute` 执行前把 `why` 剥掉，不传给处理器。

**这比原来更好**：Thought 现在是必填的，不再取决于模型心情。

## 3. 权限：挂在工具表上

三种做法，逐层变强：

| 做法 | 问题 |
| --- | --- |
| 提示词里说「不要调写工具」 | 可以被注入内容覆盖 |
| 调用后拦截 | 拦截逻辑本身可能有洞；模型已经决定要写了 |
| **不放进工具表** | 模型看不见，不可能调用 |

```python
def _loop_tools(self, ..., read_only: bool):
    for command in capability.text_commands:
        if read_only and command.writes:
            continue          # 根本不进工具表
```

这条由评测守着（`loop_tool_exposure`），
每个入口能看到哪些工具是写死的期望值。加 `knowledge-source` 那次它红了一次——
正好证明守卫有效。

## 4. 注入防护：切断链条，而不是识别攻击

### 致命三角

外部内容 + 私有数据 + 外发通道。三者齐全时，
攻击者可以「让 agent 读到被投毒的资料 → 诱导它把你的数据发出去」。

这个系统一开始只有前两条：没有通用 HTTP 抓取工具，所以
「攻击者能让 agent 做错事，但很难把数据送出去」。

**联网搜索补上了第三条腿。** 不是因为它能下载任意网页，
而是因为**查询词是模型生成的、会离开本机的字符串**——
理论上可以把成绩、目标编进查询发出去。带宽很低，但确实存在。

挡不住就至少要看得见，所以每次查询词都记进日志。

### 第一道：边界标签

```
<untrusted-data source="bilibili-subtitle">
...字幕原文...
</untrusted-data>
```

内容里的标签字面量会先被打断，防止攻击者自行闭合跳出边界。
系统提示里有一条常驻规则说明标签内只是数据。

**这一道不够。** 它依赖模型遵守规则，而遵守规则是概率性的。

### 第二道：读→写闸门

```python
if tool.returns_untrusted:
    tainted = True
if tainted and tool.writes:
    log_event("write_blocked_after_untrusted", name=tool.name)
    return "本轮已读取外部内容，不允许再执行写操作。"
```

**主循环一旦读过外部内容，本轮剩下的写操作一律拒绝。**

这一道不依赖模型识别攻击——它切断的是利用链本身。
真实验证：一句话里同时要求「查报名时间」和「记一条感受」，
搜索执行了，`feel` 被挡了，模型改口说「两件事分开说」。

### 第三道：出站检查

抹掉环境变量里的真实密钥值，删掉泄露的边界标签。
**只做精确匹配这类零误报的事**——会误伤正常回答的安全层最终会被关掉，
那比没有更糟。

## 5. 会话历史：只追加的日志

### 为什么不是内存里的列表

进程重启历史就没了。而这个 agent 是长期跑的，重启是常态（部署、崩溃、OOM）。

### 为什么不是「压缩时删掉旧消息」

压缩的目的是控制发给模型的窗口大小。
最直觉的实现是把旧消息换成一条摘要，删掉原文——但摘要是有损的，
**删掉之后就再也找不回来了**。

现在的做法：

```
{"type": "message", "mid": 1, "role": "user", "content": "..."}
{"type": "message", "mid": 2, "role": "assistant", "content": "..."}
{"type": "compaction", "through_mid": 2, "summary": "..."}
{"type": "message", "mid": 3, ...}
```

**压缩是一条标记，不是一次删除。** 重放时遇到 compaction 就把
`through_mid` 之前的消息折叠成摘要；`read_full_history()` 忽略标记，
返回全部原文。

日志只追加，从不改写已有的行。这让「历史损坏」这类问题几乎不可能发生——
最坏情况是最后一行写了一半，跳过它就行。

### 会话边界

闲置超过 `CONVERSATION_IDLE_MINUTES` 算新会话。
**这个边界是重放时按相邻记录的时间间隔推断的，不写进日志。**

写进日志的话，改主意（把 3 小时改成 1 小时）就只能影响未来的记录，
历史里的边界永远是按旧规则划的。推断出来的边界可以随时重新解释。

## 6. RAG

详细的分块与检索策略见 [rag-pipeline.md](rag-pipeline.md)。这里只记几个取舍。

### 父子分块

子块（700 字）用来匹配，父块（1200 字）用来投喂。

匹配要精度：一个具体的问题应该命中一小段具体的文字，
块越大稀释越严重。投喂要上下文：只给命中的那 700 字，模型经常缺前提。

### 分类过滤在查询期，不在索引期

试过只给 `shoes` 的块建索引——`embeddings.json` 的向量数和 `chunks.json`
的块数对不上，一致性守卫直接报错退回 BM25。

**索引必须建在全量块上。** 过滤只能发生在排序之后。

### 认不出的分类返回全部

```python
if not category or category not in known_categories():
    return chunks          # 不是空列表
```

模型会传各种自创的分类名。返回空列表的话，一个拼写差异就让整个知识库
查不到东西——而且**失败形态是「什么都没查到」，看起来像知识库是空的**。
这类错误最难归因，因为它不报错。

### 为什么还没上向量数据库

当前语料几百个块。做过一次 profile：耗时在 `json.load()`，
不在相似度计算——NumPy 算几百个 768 维向量的点积是微秒级的。

引入向量数据库解决的是「相似度计算太慢」，而这里的瓶颈不是它。

**触发迁移的具体信号**：`embeddings.json` 超过 100MB，或者加载超过 1 秒。
在那之前，多一个服务只是多一个会在半夜挂掉的东西。

## 7. 外部系统：拒绝经常伪装成「没有」

这条踩过三次，值得单独写。

### COROS 的 FIT 配额

每日约 50 次。配额用完时接口**不报错，返回空**——
和「这条活动本来就没有 FIT」返回值完全一样。

一种容易出现的误判是「COROS 只保留 90 天的 FIT」。
复查一条已经成功下载过的旧活动后，旧活动仍然可以下载，
于是「90 天截止」这个假说被证伪，真正原因是当天配额已经用光。

**教训**：区分不了两种情况时，找一个能区分它们的实验，别靠推理。

### B 站的空间接口

短时间多次请求返回 -799/412，而这**和「这个 UP 主没有视频」在结构上很接近**。
实际测试中，两个 UP 主的列表请求挨得太近，第二个直接返回空。
如果只看返回结构，很容易把限流误判成数据缺失。

### 处理方式

- 请求之间留足间隔，宁可慢
- 连续出错就熔断，不硬撑（硬撑只会把限流窗口拉得更长）
- **区分「本来就没有」和「被拒绝了」**：没有字幕的视频不计入熔断，
  否则一串无字幕视频会误触发停止
- 外部配额在自己这边也记一份（搜索的每日预算就是这么来的）

### 部分结果不该让状态倒退

翻页中途被限流时只能拿到前几页。缓存一开始是直接覆盖的，
结果某个 UP 主先缓存了较完整的历史列表，下一次只拿到前几页就把它盖掉了。

改成按 id 合并。**任何「用新结果替换旧状态」的地方都要问一句：
新结果不完整会怎样。**

## 8. 提高频率必须同时提高退让能力

字幕同步从「每天一次抓 20 条」改成「每半小时一次抓 8 条」：

|            | 每天 × 20 条 | 每半小时 × 8 条 |
| ---------- | ----------- | -------------- |
| 单轮请求爆发 | 20 条连抓    | 8 条连抓        |
| 日上限      | 20 条        | 384 条          |
| 300 条存量  | 约 15 天     | 约 1 天         |

**跑得勤 ≠ 抓得多。** 单轮批量反而要更小：一次 8 条只占 32 秒，
剩下 29 分钟全是静默期，平均请求密度比原来还低。

但代价是**限流的时候也会每半小时撞一次**。所以熔断之后写一个冷静期文件，
接下来两小时的定时任务读到它直接退出。

没有这一步的话，改频率只是把出错的代价也放大了 48 倍。

## 9. 可观测性

`trace_id` 用 `ContextVar` 传递，跨 `await` 自动携带，不用一路传参数。

日志是单行 `key=value` 的结构化事件：

```
evt=tool_call trace=ask-a1b2c3 round=0 name=list_recent_activities why=需要查看最近运动记录
evt=tool_result trace=ask-a1b2c3 name=list_recent_activities elapsed_ms=12 chars=840 untrusted=False
```

**日志要写在执行之前。** 生产环境那次卡死，工具调用完全没有日志——
因为日志写在执行之后，而执行永远没返回。写在前面就能看到它卡在哪个工具上。

长期记忆和临时缓存分开存放：`memory.json` 的 `agents` 命名空间会进提示词，
`caches` 不会。混在一起的时候，「用户选了第 3 条」这种一次性状态
会跟着进提示词，白白占窗口还可能误导模型。

### 动态架构图

Web 入口比 Discord 多一个展示能力：`trace_step`。
后端在关键节点往 SSE 流里推结构化事件：

```json
{"type": "trace_step", "module": "coros", "label": "COROS MCP", "why": "读取运动数据"}
```

前端拿到模块 id 后，只负责点亮图上的节点和连线。
这件事刻意放在观测层：动态图不参与路由，不改变工具调用，也不决定权限。
它坏了最多展示不准，不能影响回答。

映射在 `src/runtime/flow_map.py`：

- `TOOL_MODULES`：真实主 Agent 循环里，某个工具命中哪个模块
- `COMMAND_MODULES`：显式命令或快速路由时，应该展示哪条预期链路

这样两种入口都能被展示：

- 自然语言：模型调工具，后端按真实工具调用推 trace
- 显式命令：命令绕过循环，后端按命令名推一条预期链路

图上的节点按数据来源归并，而不是按函数名展开。
用户要看的是「它查了 COROS、RAG 还是长期档案」，
不是「内部调用了第几个 Python 函数」。

## 10. 评测

### 五套里有两套守的是契约

大部分评测守的是「效果」：路由准不准、检索命中率多少。
有两条守的是「契约」，性质不同：

- `loop_tool_exposure`：每个入口能看到哪些工具
- `flow_map_coverage`：每个工具都能映射到架构图上的一个模块

它们防的是**不报错的坏法**。忘了更新架构图映射，图不会崩，只会说谎——
新工具静默归到「主 Agent 循环」，看起来像什么都没查。

### 评测抓到过预期错误

有些失败不是代码错，而是评测期望写错：压缩后的消息条数、
注入用例的 `expect_leaked`、加了新工具之后的 `loop_tool_exposure`。

**这正是评测的价值**：它逼人把「系统应该怎样」写下来，
写下来之后才能被证伪。

### 留出集

开源版不内置私有评测数据集。你可以按自己的数据补充 golden set，
重点覆盖自然语言路由、只读权限、RAG 检索和工具选择。

## 11. 隐私边界

这个项目默认按单人自托管设计。仓库只提供运行时代码、部署模板和示例配置；
真实部署时产生或填写的数据都应该留在服务器上，不进入 Git：

- `.env`
- `agents/coros_report/config.toml`
- `data/`
- PDF 原文、切片结果和向量
- FIT 文件、路线图、会话历史
- Discord token、模型 key、B 站 Cookie、COROS 授权信息

公开 Web 入口也按这个边界设计：允许读取必要的展示数据，但不开放写操作。
写入类动作，例如导入视频知识、记录主观感受、同步 FIT 文件，仍建议只放在
受控的 Discord 频道或命令行环境里。
